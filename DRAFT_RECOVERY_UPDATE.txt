ㅇㄱㅁㅇ v16 — 사진 기록 임시 보관과 이어쓰기

1. 이번에 추가한 기능
- 로그인한 계정의 ‘사진 기록’ 작성 내용이 이 기기·브라우저에 자동 임시 보관됩니다.
- 사진 사본, 식물 이름, 관찰 메모, 기관, 적용한 좌표, 선택한 AI 후보를 보관합니다.
- ‘입력한 좌표 적용’을 누르지 않은 좌표 입력칸, AI 후보 전체 목록과 참고 사진, 분석 동의, 비밀번호와 인증 토큰은 보관하지 않습니다.
- 같은 계정과 같은 기관으로 돌아오면 ‘임시 기록 이어쓰기 / 임시 기록 삭제’를 선택합니다.
- 다른 계정·기관의 임시 기록은 현재 화면에 표시하지 않습니다.
- ‘내 도감’과 ‘사진 기록’은 같은 작성 화면을 유지합니다. 공유 도감·기기 기록·기관 선택 화면에서 돌아와도 복구할 수 있습니다.
- 계정 저장 요청 전에 요청 ID를 함께 임시 보관합니다. 실패 후 복구해서 같은 내용으로 저장하면 같은 ID를 재사용합니다. 서버 응답을 받기 전에 화면이 닫힌 경우에도 해당 ID로 재확인합니다.
- 계정 저장이 성공하면 해당 임시 기록을 삭제합니다. 삭제가 실패하면 오류를 표시합니다. 그 경우 다시 나타나는 임시 기록은 같은 ID로 재확인할 수 있습니다.
- 여러 탭이 같은 임시 기록을 수정하면 뒤늦은 탭의 덮어쓰기·삭제를 차단하고 경고합니다. 한 탭에서 작성하는 것을 권장합니다.

2. 보관 정책과 주의점
- 계정·기관별 마지막 작성 1개, 이 브라우저 전체 최대 20개입니다.
- 마지막 임시 보관 시점부터 7일 동안 유지합니다. 만료 자료는 다음 임시 저장소 접근 시 삭제합니다. 앱이 꺼진 동안 정확히 7일째에 실행되는 예약 삭제는 아닙니다.
- 로그아웃해도 보관됩니다. 공용 기기에서는 작성 화면의 ‘작성 및 임시 기록 초기화’를 눌러 삭제하세요. 복구 제안만 보이는 경우 ‘임시 기록 삭제’를 누르세요.
- 계정 구분은 앱 화면의 분리이며 기기 저장소를 암호화하는 기능은 아닙니다. 기기·브라우저 프로필을 다른 사람과 공유할 때 주의하세요.
- ‘기기에 임시 보관됨’을 확인한 뒤 화면을 닫으세요. 사진 처리 중이거나 저장 중인 마지막 입력은 갑자기 종료하면 잃을 수 있습니다.
- 임시 기록은 다른 기기, 다른 브라우저, 다른 사이트 주소로 동기화되지 않습니다. 같은 계정으로 다른 기기에서 확인하려면 ‘계정에 비공개 저장’이 완료되어야 합니다.
- 저장 공간 부족·차단·브라우저 데이터 삭제로 임시 기록을 잃을 수 있습니다. 이 경우 ‘임시 보관됨’으로 표시하지 않으며, 가능하면 화면을 닫기 전에 계정에 저장하세요.
- 실패한 계정 저장의 재시도는 내용이 고정됩니다. 내용을 바꾸려면 작성 및 임시 기록 초기화를 사용하세요. 이 동작은 이미 서버에 저장된 기록을 삭제하지 않습니다.
- 기관이 비활성화되어 선택할 수 없으면 그 기관의 임시 기록 복구 화면으로 들어갈 수 없습니다. 기관 관리자에게 확인하세요. 기관명 변경 후 미완료 저장 재시도가 거부되면 메모와 원본 사진을 따로 보관한 뒤 새로 작성하세요.
- 이번 변경은 로그인 후 ‘사진 기록’에 적용됩니다. 별도의 ‘기기 기록’ 메뉴의 기존 저장·백업 기능은 그대로입니다.
- 오프라인 AI 분석이나 오프라인 사이트 재실행은 추가하지 않았습니다. 임시 기록이 있어도 사이트를 열고 로그인하려면 네트워크가 필요할 수 있습니다.

3. Windows 적용 절차
(1) 기존 프로젝트 폴더 전체를 별도 폴더에 복사해 백업합니다.
(2) 이 ZIP을 별도 임시 폴더에 먼저 압축 해제합니다.
(3) 기존 프로젝트에 새 파일을 복사하되 자신의 public-config.json과 .git 폴더는 유지합니다.
    node_modules나 backend/node_modules는 복사할 대상이 아닙니다.
    ZIP 안 public-config.json은 참고용입니다. 기존 정상 작동 설정을 덮어쓰지 마세요.
(4) 명령 프롬프트(cmd)를 열고 프로젝트 루트로 이동합니다.
    cd /d "C:\Users\김준태\Documents\GitHub\bangjangsan-plant-book"
(5) 다음 순서대로 실행합니다.
    npm ci
    npm test
    npm run build
    firebase deploy --only hosting --project plant-book-84803
(6) https://plant-book-84803.web.app 에서 새로고침합니다.
    이전 화면이 계속 보이면 브라우저 새로고침을 다시 시도하거나 홈 화면 앱을 닫았다가 엽니다.
    브라우저 데이터 삭제는 기존 기기 기록까지 지울 수 있으므로 하지 마세요.
(7) GitHub Desktop에서 변경 내역을 확인하고 Commit, Push origin을 합니다.
    GitHub Push만으로 Firebase 사이트가 배포되지는 않습니다.

기존에 v13 이후 Firestore 규칙과 v12 이후 Worker가 배포되어 있다면 이번에는 Hosting만 배포합니다.
Firebase 규칙·인덱스, Cloudflare Worker, 비밀 API 키, Spark 요금제는 이번 변경으로 다시 설정할 필요가 없습니다.
기업망 인증서 설정이 필요했던 PC에서는 같은 cmd 창에서 다음을 먼저 실행하세요.
    set "NODE_USE_SYSTEM_CA=1"
TLS 인증서 검증을 끄는 설정은 사용하지 마세요.

4. 휴대폰 확인 순서
(1) 기관 선택 → 계정 A 로그인 → 사진 선택 → 이름·메모 입력 → ‘기기에 임시 보관됨’ 확인.
(2) 브라우저 탭을 닫고 같은 주소를 다시 열어 같은 기관·계정으로 들어갑니다.
(3) ‘임시 기록 이어쓰기’를 눌러 사진·이름·메모가 복구되는지 확인합니다.
(4) GPS를 직접 적용했다면 그 좌표가 복구되는지 확인합니다. 자동 GPS 요청은 하지 않습니다.
(5) 계정 저장 후 내 도감에서 확인합니다. 다시 열었을 때 임시 기록 제안이 사라져야 합니다.
(6) 새 기록을 임시 보관한 뒤 로그아웃하고 계정 B로 로그인합니다. A의 임시 기록이 보이면 안 됩니다.
(7) 같은 기관에서 A로 다시 로그인하면 A의 기록을 이어쓸 수 있어야 합니다.
(8) 다른 기관을 선택하면 그 기관의 작성 내용과 분리되어야 합니다.
(9) ‘임시 기록 삭제’와 ‘작성 및 임시 기록 초기화’도 확인합니다.
(10) 브라우저와 홈 화면 앱의 저장 공간이 분리되는 환경에서는 서로의 임시 기록이 보이지 않을 수 있습니다.

5. 개발 검증
- 기존 61개 + 신규 10개 = 71개 테스트: 통과.
- IndexedDB 모형에서 계정/기관 분리, 만료, 20개 한도, 여러 탭 충돌, 쓰기-삭제 순서, 요청 ID 유지, 오류 전파 검증.
- React 컴포넌트 테스트에서 복구 전 보존, 명시적 복구, 계정 전환 화면 초기화, 계정 저장 후 임시 기록 삭제 흐름 검증.
- 프로덕션 빌드 통과.
- Firebase/Cloudflare 실제 배포, 실기기 브라우저 복구와 저장 공간 부족 상황은 이 작업 환경에서 직접 실행하지 않았습니다. 위 휴대폰 확인 순서를 따라 확인해주세요.

이전 문서와 검증 기록은 각 버전의 참고 자료입니다. 현재 적용 절차는 이 문서를 먼저 읽으세요.
